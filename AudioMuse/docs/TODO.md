# 后续优化待办

当前已完成失败自动重试、上传幂等、最多 3 个并发消费者、核心链路测试，以及
`pending` 任务的重启后继续消费。以下内容均不影响当前单机 P0 链路运行。

## 服务重启后自动恢复处理中任务

- 现状：服务启动时会把遗留的 `transcribing`、`summarizing` 任务标记为
  `failed(WORKER_INTERRUPTED)`，避免任务永久卡住；用户可通过 retry 接口开启
  新一轮处理。`pending` 任务会由消费者自动继续领取。
- 待实现：根据已持久化的阶段和结果自动开启新轮次，并处理重复外部调用、旧轮次写回
  和进程崩溃窗口。自动恢复开启新业务轮次时增加 `attempt_no`，阶段内自动重试仍使用
  进程内局部计数。

## LLM 摘要流式输出

- 增加 `GET /v1/recordings/{id}/summary/stream` SSE 接口。
- 定义开始、增量、完成和失败事件，并处理客户端断开连接。
- 流式输出结束后仍需完成结构校验和最终结果落库，且不影响现有详情查询接口。

## 简单公网部署

- 选择云主机或容器平台，提供可访问地址和健康检查。
- 通过部署环境注入 LLM 密钥，不把密钥提交到仓库或写入日志。
- 公网开放前补充必要的访问保护与限流，并重新确认数据持久化和全局并发边界。

## 孤儿和残留文件治理

- 已实现：数据库写入失败时，对已经落盘的文件做 3 次短退避删除；删除接口使用
  `lifecycle=deleting`，文件清理失败后可再次 DELETE 继续清理。
- 待实现：
  1. 启动时扫描 `recordings` 目录，回收没有数据库记录的文件，覆盖文件落盘后、
     数据库事务提交前进程崩溃产生的孤儿文件。
  2. 使用定时后台任务处理残留文件，避免长期依赖请求内同步重试。
  3. 持久化登记多次删除失败的文件，并提供人工处理入口。
- 当前人工兜底：错误日志记录 `storage_relpath`，运维可据此定位文件，同时避免暴露
  服务器绝对路径。

## 录音记录与文件一致性提示

- 现状：详情接口以数据库记录为准；磁盘文件被人工移除时，接口不会额外报告文件缺失。
- 可选优化：详情响应增加 `file_status="missing"`，或返回明确的
  `FILE_MISSING` 错误，并补充对应测试。

## 多实例和跨机器部署

- 现状：`DataDirLock` 基于 `fcntl.flock`，只保证同一台类 Unix 机器、同一数据目录
  仅启动一个服务进程；锁会随进程退出由内核释放。
- 待实现：多实例共享存储时使用分布式执行名额或统一 worker 调度，确保跨进程全局
  并发仍不超过 3，并替换只在单机生效的文件锁。
- 数据库和本地录音文件也需要迁移到支持多实例共享的存储方案后，才能部署多个 worker。

## 事件驱动调度

- 现状：数据库中的 `pending` 行作为持久化队列，消费者每 0.2 秒原子领取任务；服务
  重启后无需重建内存队列。
- 可选优化：增加进程内事件通知以缩短空闲轮询延迟，同时保留数据库作为任务事实来源。
  如果改用 `asyncio.Queue`，需要在启动时恢复 `pending` 任务，并处理数据库提交与入队
  之间的一致性窗口。
